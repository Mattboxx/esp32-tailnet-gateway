Automation and integrations

Integrations are optional, off by default and supervised. They are not prerequisites for routing, the Service Gateway or local administration.

MQTT and Home Assistant

Two different jobs: the gateway's MQTT integration exposes its own controls and status to Home Assistant; LAN → Tailnet forwarding lets an ordinary LAN device reach a remote MQTT broker. You can use either independently. Connect MQTT devices across two homes.

  • Retained availability and state with Last Will; bounded snapshot size.
  • Discovery entities: Service Gateway rule switches and destination-test buttons, Wake-on-LAN and recovery buttons, Service watch, profile and status sensors.
  • Strict command payloads; rule commands include the rule's binding token.

Guides: MQTT, Home Assistant.

Possible-blackout automations in Home Assistant

Firmware 3.0.5 adds an optional Possible blackout MQTT event, a Blackout: notify when power returns switch, a boot-session sensor and power-on diagnostics. Enable the switch in Automation → MQTT before the next startup. Home Assistant Discovery adds the entities to your existing gateway device.

Create an automation using the event's possible_blackout type. Only a hardware power-on reset qualifies: software restarts, updates, crashes and brief Wi-Fi/MQTT disconnections do not trigger it. First startup or reconnecting a cable can look the same; this is not proof of an electrical outage.

Events are not retained. If Home Assistant starts later, retained boot metadata and a persistent helper can reconcile missed startups without repeating an action on every reconnect. See the setup and automation example for delivery limits, duplicate suppression and catch-up.

ntfy

Outage and system-event alerts, Service watch changes, and replay-protected info, Wake-on-LAN and recovery commands. Local logs are never uploaded; private details stay hidden unless you enable them. Guide: ntfy.

Power-return and restart notifications

From Firmware 3.0.4, ntfy startup alerts and the info reply use readable reset causes instead of a numeric reason. (possible blackout) is added only for a power-on reset when its notification option is enabled. Software restarts, crashes, watchdogs and voltage drops have separate descriptions.

Firmware 3.0.3 gives Telegram, email and ntfy a separate Blackout: notify when power returns option. It reports the ESP32 powering on, independently of other restarts. Crash, watchdog and low-voltage resets remain distinguishable; Telegram and email keep their separate warning/error path.

A power-on reset can also mean the first startup or a cable reconnection. The gateway cannot send while it is unpowered, prove a utility outage or measure its duration by itself. Delivery resumes when the network is available.

For Telegram/email, choose a 15–3600-second continuous-disconnection margin (60 seconds by default). Short Wi-Fi/Tailnet drops and their recoveries remain quiet; startup notifications do not wait for that timer. ntfy retains its own failure delay.

The Telegram Destination user id field includes an expandable setup guide. Notification status refresh preserves unsaved edits. Read the Telegram/email guide for TLS, retry limits and settings compatibility.

SNMP

Read-only SNMP v1/v2c with an operational subtree for monitoring systems. Unencrypted: restrict UDP 161 with the firewall and use a private community.

Security

Remote commands are as trusted as their transport. Prefer TLS, private topics and per-client broker ACLs; keep command features off unless you need them.
